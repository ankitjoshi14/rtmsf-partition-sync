The first file upload was confirmed2026-10-20T00:01:08.237Z; deletion was confirmed00:01:13.435Z, before the first native APPLIED ADD00:01:14.831Z and ACK00:01:14.865Z. A zero-byte object at exact key`gcp-native/native-r20261019n1/data/dt=soak/` finalized00:01:14.296Z, generation1792454474288135, and its native notification was subsequently acknowledged.

Independent LIST and the adapter both see that marker as present. All owned Parquet notifications have acknowledgments, but the marker keeps storage nonempty and the Hive partition present. The finite supervisor refuses successful completion and remains within its300-second settling budget. The24-hour run has not launched.

Hive3.1.2 `add_partition` calls `createLocationForAddedPartition`, which checks the supplied SD directory and calls `mkdirs` if absent. The saved GCS connector3.1.13 source shows directory creation can create a zero-sized object. This ordering is consistent with the sole file disappearing during native ADD and Hive creating a directory marker. Audit logs have not established the actual writer identity; the service connector version is not independently established.

The proposed lab driver correction uses a minimum5-second cadence with native ADD ACK before deleting each current generation, then DELETE/DROP ACK plus actual catalog/storage absence before starting another generation. At producer expiry, the same bounded settling phase must finish the outstanding ADD barrier before deletion. No marker is ignored or automatically removed. This is a serialized lifecycle soak, not proof that arbitrary concurrent data writers cannot race Hive filesystem side effects.
