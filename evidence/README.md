# Verified sample evidence

This folder contains selected results from the finalized five-graph experiment
runner. [docs/experiments.md](../docs/experiments.md) defines the experiments;
this index records what has actually been measured.

## Local activity validation — September 30, 2026

`runs/run_20260930_094050_1f83/` passed all **12 conditions**, with 100 starting
partitions per table and one repetition. It contains `activity_data.csv`,
`activity_timeline.csv`, `SUMMARY.md`, full catalog snapshots and raw evidence.
It is local/Git-ignored and does not replace the five manuscript figures below.

| Burst | RTMSF S3 requests | Immediate control S3 requests |
|---|---:|---:|
| 20 quick uploads, one new partition | 1 | 20 |
| 20 uploads spaced two seconds apart | 2 | 20 |
| One upload into each of 20 new partitions | 20 | 20 |
| 10 uploads plus 10 last-file deletions | 11 | 20 |

Requests are HEAD + GET + LIST. The immediate control was faster to first
visibility; the comparison measures work saved with the fixed Q=10/T_max=31
settings, not a universal speed advantage. The four continuous RTMSF cases each
ran for about two minutes. At 1 operation/s, 120 events required 120 attempts;
at 3 operations/s, 360 events required 130 or 170 attempts for 10 or 20 upload
targets. All showed progress while writing, then drained and passed exact final
catalog/query checks. First-new-partition visibility was about 12 or 33 seconds;
the quiet window is not an end-to-end freshness guarantee.

All **36 request components** agree across CloudWatch, CloudTrail and worker API
records; all **84 calibration requests** matched. All 851 original artifact
hashes verified, four report files regenerated byte-identically, and final
catalog/query contents were reconstructed from recorded uploads/deletes.
Live checks confirmed all 12 temporary buckets/tables removed, the worker stopped,
the prior task definition restored and trail logging off. Shared stack resources,
images and logs remain. One repetition does not establish latency distributions,
capacity limits, failure rates or the reviewer's requested window sensitivity.

Earlier attempt `runs/run_20260930_093848_cf33/` failed during S3 fixture loading,
before any condition was measured. It remains recorded; all 12 buckets and nine
created tables were cleaned. The successful run used fresh fixtures.

## What the files mean

| Files | Purpose / how created |
|---|---|
| `graph_data.csv`, `graph_1`–`graph_5` PNG/PDF | Runner collects graph points; `experiments.figures` renders them. |
| `recovery_table.md`, `checks_table.md`, `SUMMARY.md` | Generated from recorded outcomes; failures and unattempted work stay visible. |
| `report_inputs.json` | Settings and individual outcomes for offline report regeneration. |
| `source.tar.gz`, source/image identity, `observations.tar.gz` | Retained code and measurement evidence behind the reports. |
| `verification.json`, cleanup records | Separate verification/export steps; not generated by the plotter. |
| `remaining_checks/` (September 28 only) | A separate execution of the two unstarted checks; it does not rewrite the main result. |

The runner automatically creates **`runs/<execution>/`**, not a folder here.
It includes full local records. Selecting and verifying an export for `evidence/`
is a separate review step; there is no automatic publication command. Full raw
CloudTrail credential envelopes are excluded from these selected exports.
Regeneration commands are in [the runbook](../docs/aws.md).

Older pilots, incomplete exploratory runs, diagnostic notes and scratch source
copies have been moved to a separate local archive, not discarded or reclassified
as successful results. They are not inputs to the current experiment protocol.
The archived execution IDs for the September 28 bundle are
`p20260928_063557_2b99` and `p20260928_083133_0cf5`.
